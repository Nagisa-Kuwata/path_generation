## 1. 迷路生成アルゴリズム

### Decision
**Recursive Backtracking（再帰的バックトラック / DFS ベース）** を採用する。

### Rationale
- 実装が単純で Rust の `Vec` スタックに自然にマッピングできる。
- 必ず連結した迷路（すべてのセルが到達可能）を生成する。
- 開始位置→目標位置のルートが **恰も 1 本** になる木構造（スパニングツリー）を生成できる。
- シードを固定すれば完全に再現可能。

### Alternatives Considered
| アルゴリズム | 却下理由 |
|-------------|---------|
| Prim's Algorithm | ランダム性は高いが実装コストがやや高い |
| Kruskal's Algorithm | Union-Find が必要でセルサイズ 240×240 には過剰 |
| Wilson's Algorithm | ループ消去乱歩は均一分布だが収束が遅い |

### 補足：グリッド設計
- 12 m ÷ 0.05 m = **240 セル**（1 辺）
- セルの種類：`Wall`（壁）・`Passage`（通路）・`Unknown`（ロボット未観測）
- 壁厚 0.1 m = 2 セル分。通路セルと壁セルが交互に並ぶグリッド表現（奇数インデックス = 通路）
- 実際の通路幅 = 1 通路セル + 両側壁 → 最小通路幅は壁厚を除いて設計する
- ロボット幅 0.5 m = 10 セル → 通路幅は最低 10 セル（= 0.5 m）以上を保証する

## 2. LRF レイキャスティング

### Decision
**DDA（Digital Differential Analyzer）アルゴリズム** を用いたグリッドレイキャスティング。

### Rationale
- グリッドベースの迷路に対して O(距離) の高速なレイ交差判定が可能。
- Rust の整数演算で実装しやすく、浮動小数点誤差が少ない。
- 50 Hz × 720 本（360° / 0.5°）= 36,000 レイ/s を単一スレッドでも十分処理できる。

### Alternatives Considered
| 手法 | 却下理由 |
|------|---------|
| ブルートフォース全セル判定 | O(n?) で 240×240 グリッドには遅すぎる |
| BVH/BSP ツリー | 動的な迷路には不向き、実装コスト大 |

## 3. 経路生成アルゴリズム

### Decision
**A\* アルゴリズム**（ヒューリスティック = ユークリッド距離）を採用する。  
未知領域への探索戦略として **最近傍未知フロンティア** をサブゴールに設定する。

### Rationale
- A\* は最適経路保証があり、Rust での実装実績も豊富（`BinaryHeap` が優先キューとして利用可能）。
- 保有マップが更新されるたびに再計算（50 Hz）するため、軽量なヒューリスティックが必須。
- 目標が未到達の間は「最近傍未観測セル（フロンティアセル）」をサブゴールとすることで、
  未知領域を効率的に探索する。

### Alternatives Considered
| アルゴリズム | 却下理由 |
|-------------|---------|
| Dijkstra | ヒューリスティックなしで 240×240 グリッドは遅い |
| D\* Lite | 動的マップ更新に特化するが実装が複雑 |
| RRT | 連続空間向け。グリッドベースには過剰 |

## 4. ロボット移動モデル

### Decision
**連続座標（最小単位 0.05 m）上のホロノミック移動**。  
毎シミュレーションステップで進行方向ベクトルを正規化し、速度 1 m/s × Δt を積分して位置更新。

### Rationale
- 姿勢を持たないため、速度ベクトルをそのまま位置に加算するだけで実装できる。
- 経路ウェイポイント間の補間を線形補間で行い、次のウェイポイントへ向かうベクトルを進行方向とする。

### Δt の設計
- UI 更新レート 30 fps → Δt ? 33.3 ms
- LRF 更新 50 Hz → Δt = 20 ms（LRF サイクルを基準ステップとする）
- ロボット位置更新とLRF更新を同一ループで処理し、経路再生成もこのループで行う。

## 5. フロンティア探索（未知領域の最近傍探索）

### Decision
保有マップ上の **既知通路セルに隣接する未観測セル（フロンティアセル）** を列挙し、  
ロボット現在位置から最短距離のフロンティアセルをサブゴールとする。

### Rationale
- BFS でフロンティアセルを探索 → O(既知セル数) で十分高速。
- 目標位置がまだ既知マップ内にない場合のデフォルト戦略として明快。
- ゴールが既知領域に入った瞬間に A\* でゴール直行に切り替える。

## 6. UI フレームワーク（Rust）

### Decision
**`egui` + `eframe`** を採用する。

### Rationale
- Pure Rust の即時モード GUI で、クロスプラットフォーム（Windows/Linux/macOS/WASM）対応。
- カスタム描画（`epaint`）で迷路・ロボット・LRF点群・経路を自由に描画できる。
- 依存が少なく、`cargo audit` での脆弱性管理が容易。
- 30 fps の描画は `eframe` のデフォルトループで達成可能。

### Alternatives Considered
| フレームワーク | 却下理由 |
|--------------|---------|
| Bevy | ゲームエンジンとして機能過剰。シミュレータ用途には重い |
| iced | 即時モードでなく Elm アーキテクチャ。リアルタイム描画に向かない |
| piston | メンテナンスが停滞気味 |
| wgpu 直接 | 低レベルすぎ、UI ウィジェット実装コストが大きい |

---

## 7. 乱数生成

### Decision
**`rand` クレート + `rand_chacha::ChaCha8Rng`** を採用。

### Rationale
- ChaCha8 は決定論的で高速。シードを固定すれば完全再現可能。
- `rand` は Rust エコシステムの標準乱数クレートで `cargo audit` での監視も容易。
